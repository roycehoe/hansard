# 0008. Pages render on the client

The site is a React app that draws every page in the browser. The server sends `index.html` with a per-page title, description, Open Graph tags and canonical link written into the head (`api/middleware/frontend.py`), and an empty `<div id="root">`. The page text arrives only after the JavaScript loads and calls the API. The competitor review of 28 October 2026 measured what this costs. Raw HTML is 2.6 to 2.8 KB with no debate text. On a throttled phone the first paint is 3.9 s on the home page and 2.7 s on a report, against 1.7 to 2.0 s on SPRS and sgparliament.com. sgparliament.com renders its debate pages on the server, and a web search found its pages indexed and none of ours, though openhansard.sg was one day old. The review proposed progressive enhancement: the Python server would write the heading, details and speech text into `#root` as plain HTML, and React would take over when it loaded. Full React server rendering was ruled out because a Node renderer would not fit the 0.5 GB container and the Docker build has no database to prerender from. On 28 October 2026 Royce decided against progressive enhancement. Pages keep rendering on the client only. The server writes into the head (title, description, Open Graph, canonical, JSON-LD) and nothing into the body. The site does not take on a second copy of each page layout in Python that has to be kept in step with the React one, along with the size cap, takedown check and cache rule it would need. In return, crawlers that don't run JavaScript and readers with scripts off get no text, and slow phones wait for the JavaScript before they see any text. Google runs JavaScript before it indexes a page, so it can still read the text. Reopen this decision only with measured evidence, such as Search Console showing reports left unindexed because they render on the client.

## Amendment, 7 Nov 2026

Royce set a new goal, to rank above sgparliament.com on Google for searches about a topic, an MP or a quote. "Measured evidence" now means one dated check. On 27 November 2026 the Page indexing report for the report sitemaps and one URL Inspection live test decide it. If under half of the submitted reports are indexed (23,259 of 46,517 today), or the live test shows no speech text, this decision reopens for report pages only. The server would then write the title, date, speakers and speech text as plain HTML that React replaces, with no second copy of the layout. That text passes the same takedown check as the report page, and a Speech link keeps its canonical on the Report. If half or more are indexed, the decision stands even when sgparliament.com ranks above us, because body text would mainly help indexing. The work then moves to links from other sites, and the check runs again three months later.

## Amendment, 9 Nov 2026

Royce replaced the 27 November test. The Page indexing report of 9 November 2026 showed about 14,000 pages indexed across all page types, 2,983 crawled and not indexed, and 31,890 discovered and never fetched. Of the pages Google had fetched and judged, about 82% were indexed. A URL Inspection live test of `/reports/bill-35`, a page on the Crawled list, showed the entire page. The old test counted the discovered pages against the site, but Google has not fetched them, and text in the HTML would not change that. On 27 November 2026 the test uses the Page indexing report filtered to the report sitemaps. The share of fetched reports indexed is Indexed divided by the sum of Indexed and "Crawled, currently not indexed". Pages in "Discovered, currently not indexed" do not count. If that share is under 70%, or a URL Inspection live test shows no speech text, this decision reopens for report pages only. The rest of the 7 Nov amendment stands, including what the server would write, the takedown check, the Speech canonical, the move to links from other sites, and the check again three months later.

## Amendment, 12 Nov 2026

Royce reopened this decision on 12 November 2026 for report pages, to reach AI readers. ChatGPT's search crawler and its page reader, like most AI fetchers, do not run JavaScript, so the premise above that a crawler can still read the text holds for Google but not for them. That day curl with the OAI-SearchBot, GPTBot and ChatGPT-User user agents got status 200 and an empty `#root` for `/reports/written-answer-na-25276`, and ChatGPT reported no readable lines on the page. The server now writes each report's title, sitting date, speaker labels and paragraphs into `#root` as plain HTML, as the 7 Nov amendment describes, and React replaces it when it loads. Since 14 November 2026 a browser that runs JavaScript hides this text, and the server text the later amendments add, because it flashed unstyled for about 50 ms on each reload before React replaced it. The inline script in `app/index.html` adds a `js` class to `<html>`, and `app/src/index.css` hides the element marked `data-page-text` under that class, so readers with scripts off and fetchers that run no CSS still get the text. The text comes from the same service as `GET /api/reports/{slug}`, so it passes the same takedown check, and a Speech link keeps its canonical on the Report. It prints the stored text unchanged (ADR 0006). If the database read fails, the page keeps the empty `#root` it has today. The page carries the whole report with no size cap, because the API already sends the whole report in one answer and the HTML is smaller than that JSON: on 12 November the Committee of Supply report `budget-2902` had 183 KB of text against a 322 KB API answer. Nothing new is cached. The page keeps `Cache-Control: no-cache`, so the server reads the report on every request.

The home page also gets a short block in `#root`: one paragraph on what the site is, and links to each Parliament's sittings, the latest sittings and the people list, so a reader without JavaScript can find its way towards the reports. Person and sitting pages keep an empty `#root` for now, and so does search, which `robots.txt` still disallows. The 27 November check still runs for its own purpose, to measure how much of the report sitemap Google indexes. Its result no longer decides whether report pages carry server text.

Later on 12 November 2026 Royce extended the server text to sitting pages, so `/sittings/{date}` lists each report of that sitting and `/sittings?parliament=N` lists each sitting of that Parliament, both read through the services the sitting API uses, so a report the takedown check hides drops out of both lists as it does on the React page. Person pages still keep an empty `#root`.

## Amendment for search, 12 Nov 2026

The amendment above left search out, and `robots.txt` disallowed `/search` for every agent. Later on 12 November 2026 ChatGPT told Royce it could open Open Hansard "but its interactive search results were not available through my browsing interface", and it answered from other archives instead. That day curl with the ChatGPT-User user agent got status 200 and an empty `#root` for `/search?q=default+interest`, while `/api/search/speeches?q=default+interest` returned 11 KB of JSON. Royce extended the server text to search.

On `/search` the server now writes the first page of speech matches into `#root`. It opens with one line on what the archive covers (unofficial, English only, since 1955), so a reader can tell what an empty result means. Then come the match count, capped as the API caps it, and each match's report title, sitting date, speaker label and snippet, linked to its paragraph the way the React results link it. A link to the next page follows when there is one, and a link to the title matches tab, which stays on the client. The server reads the address parameters the React page reads, plus `page`, and calls the same speech search service as `GET /api/search/speeches`, so the takedown check, the three search slots, the 10-second timeout and the search counts all apply. A busy search, one that runs out of time and one the API would refuse each get one line, in the React page's words where it has them, because an empty page reads to an AI as no results. If the database read fails, `#root` stays empty, as on other pages.

The server writes search results only when the request has no `Sec-Fetch-Dest: document` header. Browsers send that header on every page load, and curl, ChatGPT's page reader and most other fetchers do not. Without the gate every visit by a person would run its search twice, once on the server and once from React, against only three search slots. A browser gets the same page as before. Because the body now depends on that header, the `/search` page carries `Vary: Sec-Fetch-Dest`. It already carried `Cache-Control: no-cache`, and Cloudflare answered `cf-cache-status: BYPASS` for it on 12 November, so no shared cache stores a fetcher's copy and hands it to a browser, or the reverse.

`robots.txt` keeps `Disallow: /search` for `User-agent: *` and adds a group each for ChatGPT-User, Claude-User and Perplexity-User that allows every path. These agents fetch a page when a person asks a question, and they do not crawl. A crawler obeys only the most specific group that names it, so each new group carries its own `Allow: /`, and the `Sitemap` line stays outside every group. Search engine crawlers still skip `/search`.

The home page text also gains a line that shows the search address, such as `https://openhansard.sg/search?q=your+words`, and a plain form that sends its words to `/search`.

## Amendment for person pages, paragraph ids and title matches, 12 Nov 2026

Later on 12 November 2026 Royce extended the server text to person pages and to the title matches tab of search, and gave each report paragraph an id.

On `/people/{id}-{slug}` the server now writes the person's name as stored, their memberships as the React page's Memberships table shows them (the Parliament, the party and the constituencies, as the record prints them), a link to search their speeches, and links to their 20 most recent reports, which is the first page of reports the React page loads. The memberships come from the same service as `GET /api/people/{id}` and the reports from the same service as `GET /api/people/{id}/reports`, so a report the takedown check hides drops out of the list as it does on the React page. A person who does not exist still answers 404 with an empty `#root`. If the database read fails, `#root` stays empty, as on other pages. Nothing is cached, so the server reads the person and their reports on every request.

The head of a found person page also carries a schema.org `Person` script with two fields, the stored name and the canonical URL. It names no party or seat, because both can change within one Parliament and the page text already prints them beside their Parliament. It carries no identifier besides the URL. ADR 0004 calls person ids the weak link in the site's URLs, so the script promises no more than the canonical link does.

Each paragraph of a report's server text now carries the id the React page gives it, `s` followed by the paragraph's ordinal, so a link to `#s12` lands on that paragraph whether or not React has loaded. The search text already links its matches that way. ADR 0004 still applies, and `#s12` can lead to a different paragraph after the archive is rebuilt. The server text does not print the checked Speech link (`?s=12&q=...`) beside each speech. That is left for a later decision.

The search amendment kept the title matches tab on the client. When the address has `tab=titles` and the React page offers that tab, which it does unless a constituency is chosen or a person is chosen with no words, the server now writes the first page of report title matches in place of speech matches. They come from the same service as `GET /api/search/reports`, called with the parameters the React page sends it. The `Sec-Fetch-Dest` gate, the three search slots, the 10-second timeout, the search counts and the one-line notes apply to title matches as they do to speech matches.

## Amendment for AI citations, 21 Nov 2026

On 20 November 2026 Royce ran a study of how AI assistants answer questions about Singapore Parliament with and without Open Hansard. In all 20 lawyer conversations the assistant took the volume and column from another source, such as a judgment, SPRS or sgparliament.com, because our server text gave neither. A lawyer cites a report by volume and column, so a page that omits them sends that reader elsewhere. Page changes that follow from the study go under this heading.

A report's server text now carries a citation line under the date: `Singapore Parliamentary Debates, Official Report (20 November 1975) vol 34 at cols 1379 to 1397`. The wording is what Copy citation builds in the app, with the column range added, and the Legislative Assembly title for Parliament 0. A report with one column reads `at col N`. A report whose row stores no column range reads `... vol 96. The record gives no column numbers for this report.` The range comes from the report row's `column_start` and `column_end`, read through `get_report_column_range` in `services/report.py`, because a range computed from the paragraphs would inherit a misprinted column. The API response does not carry the range, since the app has no use for it. Each paragraph whose column differs from the one before it gets a `col. N` marker, as the app's marker reads, where the app marks every paragraph. A paragraph whose column note differs from the paragraph before gets one too, printing the record's number with our reading of it beside it, in the words of the app's column note tooltip (ADR 0006), so a run of paragraphs under one misprinted column carries the note once. The markers and notes now live in `RowSpeech.tsx` and `TooltipColumnNote.tsx` and in `middleware/page_text.py`, and the two must agree.

A sitting's server text now also says what each report is and, for some, who. Under each title, and its subtitle if it has one, a line gives the type in the words of the app's tag. A question names the members who asked it, linked to their person pages. A Bill or motion names the first speaker outside the chair, as "spoke first", because the first speaker of a resumed debate is not always the member who moved it. Every other type prints the type alone, and so does a Bill or motion whose first speaker is not matched to a person. On 20 November 2026 citizen-5's tier B run cited sgparliament.com's sitting page for which reports were questions, because ours listed bare titles. The React sitting page shows the type but not the member, so the server text now says more than the page a browser shows, and the two lists differ until the app shows the member too. The names come from two batched reads per request, and nothing is cached.

Later on 21 November 2026 Royce widened the person page's list and linked the speaker labels. The person page now lists every report of the person, not the first 20, grouped by Parliament with the newest first. Each group has a heading, a count line (`925 reports`, `1 report`) and its rows in the order the React list uses, each row giving the linked title, the sitting date and the type in the app tag's words. The `Showing 20 of 1,467.` line is gone. In a report's text, each speaker label that prints now links to `/people/{id}-{slug}` wherever the report response matches the paragraph to a person, the chair included, as the React report page links it. A label with no matched person prints as before. The reason is that no person page of ours appeared in any ChatGPT result in 60 conversations, and sgparliament.com's MP pages were ChatGPT's route to old debates. The links give a crawler a path from every report page it already holds to the person page, and the full list gives that page something to cite. On the 21 November copy, Louis Ng's page (1,467 reports) was 278 KB, 53 KB gzipped, built in 0.09 s, and the largest page, Desmond Lee's, was 446 KB, 86 KB gzipped, built in 0.11 s. ADR 0004 calls person ids the weak link in our URLs, so each added link raises the cost of an id changing. The 12 November sentence above about the 20 most recent reports no longer holds.

Later on 21 November 2026 Royce ruled that `/about`, `/about/coverage` and `/people` carry text too. On 20 November, 9 Claude conversations and 2 ChatGPT ones got only a title from these pages, and citizen-3's Claude runs said our pages do not name who runs the site, which About's last line does. About and Coverage print the React pages' copy word for word, and Coverage prints the counts from the service behind `GET /api/coverage`, which caches them in process. People prints every person in the order of `GET /api/people`, each name linked to `/people/{id}-{slug}`, with the Parliament, constituency and party line the React list shows and its "Sitting MP" mark. The contact address comes from `CONTACT_EMAIL`, a run-time setting, because `VITE_CONTACT_EMAIL` exists only at build time; with it unset, the lines that name the address are left out, as the React pages leave them out. The cost is that About and Coverage copy now lives in React and in Python, so each wording change is made twice, and People is 119,580 bytes (17,449 gzipped) on the 21 November copy, built on every request and then hidden from browsers. `/researchers` stays empty: `.do/app.yaml` builds the site with an empty `VITE_RESEARCHERS_FORM_URL`, so the live bundle sends that address to the home page, and text there would describe a page no person can open.
