# 0008. Pages render on the client

The site is a React app that draws every page in the browser. The server sends `index.html` with a per-page title, description, Open Graph tags and canonical link written into the head (`api/middleware/frontend.py`), and an empty `<div id="root">`. The page text arrives only after the JavaScript loads and calls the API. The competitor review of 28 October 2026 measured what this costs. Raw HTML is 2.6 to 2.8 KB with no debate text. On a throttled phone the first paint is 3.9 s on the home page and 2.7 s on a report, against 1.7 to 2.0 s on SPRS and sgparliament.com. sgparliament.com renders its debate pages on the server, and a web search found its pages indexed and none of ours, though openhansard.sg was one day old. The review proposed progressive enhancement: the Python server would write the heading, details and speech text into `#root` as plain HTML, and React would take over when it loaded. Full React server rendering was ruled out because a Node renderer would not fit the 0.5 GB container and the Docker build has no database to prerender from. On 28 October 2026 Royce decided against progressive enhancement. Pages keep rendering on the client only. The server writes into the head (title, description, Open Graph, canonical, JSON-LD) and nothing into the body. The site does not take on a second copy of each page layout in Python that has to be kept in step with the React one, along with the size cap, takedown check and cache rule it would need. In return, crawlers that don't run JavaScript and readers with scripts off get no text, and slow phones wait for the JavaScript before they see any text. Google runs JavaScript before it indexes a page, so it can still read the text. Reopen this decision only with measured evidence, such as Search Console showing reports left unindexed because they render on the client.
